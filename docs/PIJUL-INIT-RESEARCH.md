# 🌈 PIJUL initialization research

## 🌈 Purpose

Re-evaluate the assumption that GitCenter needs a local supervisor merely to create a Pijul repository. GitCenter's existing Git implementation is a useful architectural precedent: it constructs a bare Git repository directly through `ZeroFS`, writing the repository files and objects itself. It does not invoke `git init`.

This document records what is known, what is not yet verified for the pinned Pijul version, and the implementation gate for a native `.pijul` bootstrap.

## 🌈 GitCenter's existing initialization model

In `main/dist/js/git.js`, `Git.init(root, zeroPage, name, email)` writes the Git repository layout through `ZeroFS.writeFile`:

- `HEAD`;
- `description`;
- `config`;
- an empty tree and initial commit object;
- `refs/heads/master`.

The `Git` class also reads and writes Git objects directly through `ZeroFS`. This is an in-application VCS implementation, not a wrapper around the Git executable.

Therefore, the ability to create a VCS data directory does not, by itself, imply a need for a separate local service. Pijul initialization must be evaluated against the same storage capability before introducing a supervisor for this purpose.

## 🌈 What upstream documents

The Pijul manual describes `pijul init` as initializing an empty repository, with the default channel named `main`:

- https://pijul.org/manual/reference/init.html
- https://pijul.org/manual/getting_started

The official Pijul repository format document describes a modern repository containing a recorded change. Its example includes:

```text
.pijul/
├── changes.<suffix>
├── hooks/
├── id
├── local/
│   └── ignore
├── meta.toml
├── patches/
│   ├── <change-hash>.gz
│   └── <change-hash>.sig
├── pristine/
│   ├── db
│   └── db.lock
└── version
```

Source: https://nest.pijul.com/pijul/nest:main/tree/AX7NN2MQXFV32.EYYUG

The document explicitly identifies `pristine/db` as a Sanakirja database containing B-tree structures. It is not an ordinary text file and must not be replaced with an empty placeholder.

An older 2020 initialization walkthrough shows a different historical layout (`changes/`, `config`, and `pristine/db0` plus a lock file):

- https://discourse.pijul.org/t/1-0-0-alpha-usage-proto-documentation/590

That historical layout is evidence of format evolution, not a valid template for the current pinned release.

## 🌈 Compatibility gap: pinned version

GitCenter's PIJUL-02 bridge pins Pijul `1.0.0-beta.24`.

At the time of this research, no byte-for-byte empty repository fixture generated by exactly `1.0.0-beta.24` has been captured and checked into this repository. The modern upstream format page documents a repository with a change, not a pristine empty initialization. The 2020 example is from an older generation.

Consequently, the following are **not yet verified** for `1.0.0-beta.24`:

- the exact empty `.pijul` directory tree immediately after `pijul init`;
- exact contents of text metadata files;
- whether the pristine database is deterministic across initializations;
- which files contain generated identifiers or other per-repository values;
- lock-file creation and lifecycle requirements;
- whether a database fixture can safely be copied and reopened by the pinned version.

## 🌈 Required fixture experiment

Before implementing a JavaScript bootstrap, generate two independent empty repositories with the exact pinned binary:

1. Record the binary version and checksum.
2. Run `pijul init --channel main` in two fresh directories.
3. Capture a recursive listing including hidden files, file sizes, file types, and SHA-256 hashes.
4. Capture the contents of every text file.
5. Compare both trees to distinguish constants from generated values.
6. Run `pijul channel`, `pijul log --hash-only --limit 1`, and the bridge's `inspect` operation against both repositories.
7. Close all processes, reopen both repositories, and repeat inspection.
8. Record whether the pristine database and lock files can be safely copied, and which fields must be regenerated.

The fixture must be produced by the pinned release, not reconstructed from a historical blog post or inferred from a repository containing recorded changes.

## 🌈 Implementation decision

The architecture must distinguish two separate capabilities:

1. **Filesystem bootstrap:** creating the repository directory and writing a verified initial `.pijul` layout into the storage exposed to GitCenter. This may be implemented with the existing `ZeroFS` path, just as Git initialization is implemented today.
2. **Pijul-native operations:** reading and mutating the pristine database, recording changes, managing channels, and exchanging changes. These require correct Pijul semantics and may continue to use the Rust bridge.

A supervisor must not be introduced solely because Pijul has a binary pristine database. First determine whether a versioned, validated pristine fixture plus generated metadata can be safely installed through `ZeroFS`. If the database requires runtime initialization through Sanakirja/libpijul, that specific operation may need a native component; it still does not automatically justify moving the entire repository outside the ZeroNet site tree.

Do not create a directory that merely looks like `.pijul` and label it a valid repository. Do not write placeholder bytes to `pristine/db`.

## 🌈 Consequences for PIJUL-03

PIJUL-03B must begin with the fixture experiment and a ZeroFS capability audit. It must not assume a separate bridge-managed storage root or a local HTTP supervisor is required for repository creation.

The PIJUL-03A metadata schema is provisional with respect to the final storage location. Its `storage_path` semantics must be revisited after the experiment. No migration or schema change should be made until the in-site versus external-storage decision is supported by a working prototype.
